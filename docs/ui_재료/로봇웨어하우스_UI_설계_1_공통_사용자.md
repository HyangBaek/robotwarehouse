# 1부. 공통

## 1. 문서 목적

기존 로봇 창고 VR UI를 기반으로 사용자 조작 UI를 개선하고, 운영자 및 개발자가 시스템 상태와 실행 과정을 확인할 수 있는 관리자/디버그 UI를 설계한다.

전체 UI는 다음 세 가지 관점으로 분리한다.

| 모드 | 하는 일 | 답하는 질문 |
|---|---|---|
| **User Mode** (사용자 UI) | 작업을 쉽게 수행 | 무엇을 해야 하는가 |
| **Admin Mode** (관리자 UI) | 시스템 상태를 빠르게 확인 | 현재 시스템에서 무슨 일이 일어나고 있는가 |
| **Developer Mode** (개발자 UI) | 문제의 원인을 추적하고 상세 데이터를 확인 | 왜 그렇게 되었는가 |

## 5. 최종 설계 방향 — 세 단계 분리

관리자 UI에 모든 기능을 넣지 않는다.

일반 관리자에게 필요한 정보:

```text
Dashboard
Connection
Agent
Simulation
Logs
Scenario
Test
```

개발자에게 필요한 상세 정보:

```text
Raw JSON
API
Performance
Grid Coordinate
WebSocket Payload
Detailed Debug
```

따라서 최종적으로 세 단계로 분리한다.

```text
┌──────────────────────────┐
│ USER                     │
│ 일반 사용자               │
└──────────────────────────┘

┌──────────────────────────┐
│ ADMIN                    │
│ 운영 / 시연 / 모니터링    │
└──────────────────────────┘

┌──────────────────────────┐
│ DEVELOPER                │
│ 디버깅 / 원인 분석        │
└──────────────────────────┘
```

## 6. 디자인 시스템

### 6.1 Typography

세 단계로 단순화한다.

| 용도 | 권장 시작 크기 |
|---|---:|
| Title | 32~40 px |
| Section | 24~28 px |
| Body | 18~22 px |
| 보조 정보 | 16 px 이하 사용 자제 |

Quest 2에서 실제로 읽어야 하는 정보는 지나치게 작게 만들지 않는다.

### 6.2 색상 체계

색상은 장식보다 의미 전달에 사용하고, 의미를 모든 화면에서 일관되게 유지한다. 기본 배경/패널/텍스트는 어두운 배경과 밝은 텍스트를 기본으로 한다.

**상태 색상** — 시스템·패널·로봇 상태 표시 (주로 관리자/개발자 UI)

```text
● GREEN   정상
● YELLOW  주의 / 대기
● RED     오류
● BLUE    진행 중 / 처리 중
● GRAY    비활성 / 미연결
```

**행동 색상** — 버튼과 안내 문구 (사용자 UI)

| 색상 | 의미 |
|---|---|
| 파랑 | 주요 행동 / 실행 |
| 초록 | 정상 / 완료 / 확인 |
| 주황 | 사용자 주의 |
| 빨강 | 오류 / 위험 |
| 회색 | 보조 기능 / 비활성 |
| 흰색 | 일반 텍스트 |

예:

```text
[ 창고 만들기 ]   → 파랑
[ ✓ 확인 ]        → 초록
[ ⚠ 다시 확인 ]   → 주황
[ 오류 ]           → 빨강
[ 취소 ]           → 회색
```

### 6.3 버튼 크기와 배치

VR에서는 작은 버튼을 피한다. 버튼은 컨트롤러 포인터로 쉽게 선택할 수 있도록 충분한 클릭 영역과 간격을 확보한다.

현재 UI의 다음과 같은 작은 버튼은 사용자 패널에서는 제거한다.

```text
W1  W2  W3  W4  W5  W6
```

사용자 버튼 예:

```text
┌─────────────────────────────┐
│         창고 만들기          │
└─────────────────────────────┘
```

```text
[        생성        ]
```

관리자 버튼 예:

```text
[ Run ]
[ Stop ]
[ Restart ]
```

특히 서로 다른 행동을 하는 버튼은 충분히 떨어뜨린다.

```text
[ 다시 만들기 ]       [ ✓ 확인 ]
```

### 6.4 버튼 상태

모든 버튼의 상태는 다음 4가지로 통일한다.

```text
NORMAL
  ↓
HOVER
  ↓
PRESSED
  ↓
DISABLED
```

| 상태 | 뜻 |
|---|---|
| Normal | 기본 버튼 상태 |
| Hover | 컨트롤러 포인터가 올라간 상태 |
| Pressed | 버튼을 누른 상태 |
| Disabled | 현재 단계에서 사용할 수 없는 상태 |

예를 들어 창고 확인 전에는:

```text
[ 시뮬레이션 실행 ]
```

을 Disabled 상태로 처리하거나, 단계상 아예 숨길 수 있다.

### 6.5 위험 버튼

다음 명령은 확인을 거친다.

- Stop
- Reset
- Clear
- Delete
- Restart

예:

```text
┌──────────────────────────────┐
│ Restart simulation?          │
│                              │
│ Current result will stop.    │
│                              │
│ [ Cancel ]     [ Restart ]   │
└──────────────────────────────┘
```

## 7. 모드 진입과 전환

### 7.1 진입 구조

```text
USER MODE
    │
    │ ⚙
    ▼
┌─────────────────────┐
│ System              │
│                     │
│ User Mode           │
│ Admin Mode          │
└─────────────────────┘
          │
          ▼
      ADMIN MODE
          │
          ├── Operator
          │
          └── Developer
```

Developer Mode는 필요하면 PIN이나 개발자 전용 진입 절차를 둘 수 있다.

### 7.2 사용자 → 관리자 전환

사용자 화면에서는 관리자 진입 버튼을 작게 표시한다.

```text
⚙
```

선택 시:

```text
┌─────────────────────────┐
│ 관리자 모드              │
├─────────────────────────┤
│ 관리자 PIN              │
│                         │
│ [ ● ● ● ● ]            │
│                         │
│        [ 확인 ]          │
└─────────────────────────┘
```

개발 중에는 별도의 개발 옵션을 사용할 수 있지만, 제출/시연용 빌드에서는 관리자 진입을 제한하는 방향을 고려한다.

### 7.3 관리자 → 사용자 전환

Admin 화면 왼쪽 아래:

```text
┌────────────────┐
│ ← User Mode    │
└────────────────┘
```

한국어 표기 예:

```text
[ ← 사용자 모드 ]
```

선택 시:

```text
사용자 모드로 돌아갈까요?

[ 취소 ]      [ 확인 ]
```

확인하면 User Canvas를 다시 활성화한다.

Unity에서는 User Canvas와 Admin Canvas를 동시에 보여주지 않고 현재 모드에 맞는 Canvas를 활성화하는 구조를 사용한다.

## 9. 데이터 연결 구조

UI가 서버를 직접 여기저기 호출하지 않도록 중간 Data Manager 계층을 둔다.

```text
                    Server
                      │
               REST / WebSocket
                      │
                      ▼
              ┌──────────────┐
              │ Data Manager │
              └──────┬───────┘
                     │
       ┌─────────────┼─────────────┐
       ▼             ▼             ▼
   User State    Admin State   Debug State
       │             │             │
       ▼             ▼             ▼
   UserCanvas    AdminCanvas   DeveloperCanvas
```

같은 데이터를 모드별 목적에 맞게 다르게 표현한다.

예를 들어 `sim_ready` 이벤트가 들어오면:

### User

```text
시뮬레이션 준비 완료
[ 재생 ]
```

### Admin

```text
Simulation
READY

Robots 4
Steps 1102
Orders 50
```

### Developer

```text
WebSocket
sim_ready

Payload
{
 ...
}

Timestamp
14:32:15
```

# 2부. 사용자 UI

## 13. 사용자 UI 설계 방향

현재 사용자 UI와 관련 시나리오를 바탕으로, Quest 2에서 사용하는 **사용자용 조작 UI**를 개선하기 위한 설계 내용을 정리한다.

기존의 기능을 없애기보다 사용자의 실제 작업 흐름에 맞춰 재배치하고, 3D 창고를 주 화면으로 확보하면서 필요한 작업 패널만 단계별로 제공하는 것이 기본 방향이다. 관리자/개발자용 UI 및 디버그 패널은 UI 설계 ②에서 별도 모드로 설계하여 사용자 UI와 충돌하지 않도록 분리한다.

### 13.1 화면 구조

기존의 하나의 큰 패널에 여러 기능을 동시에 배치하는 방식에서 다음 구조로 변경한다.

```text
QUEST 2 사용자 시점

┌─────────────────────────────────────┐
│                                     │
│              3D 창고                │
│                                     │
│       🤖       🤖                   │
│                                     │
│                         ┌─────────┐ │
│                         │ 사용자  │ │
│                         │ 작업    │ │
│                         │ 패널    │ │
│                         └─────────┘ │
│                                     │
└─────────────────────────────────────┘
```

### 13.2 기본 원칙

- 3D 창고가 주 화면
- 사용자 패널은 필요한 작업을 수행할 때만 표시
- 패널은 World Space Canvas 방식으로 구성하는 것을 권장
- 사용자 시점 기준 오른쪽 아래 영역을 기본 위치로 고려
- 개발자 정보는 사용자 패널에서 제거
- 한 화면에서 가장 중요한 행동은 하나의 Primary Action으로 지정

## 14. 사용자 패널 공통 구조

모든 화면은 가능한 한 동일한 구조를 사용한다.

```text
┌─────────────────────────────────┐
│ 제목                       상태 │
├─────────────────────────────────┤
│                                 │
│             Content             │
│                                 │
│                                 │
├─────────────────────────────────┤
│          Primary Action         │
└─────────────────────────────────┘
```

### Header

예:

```text
로봇웨어하우스             ● 연결됨
```

또는

```text
② 창고 확인
```

사용자에게 필요한 연결 상태만 표시하고 다음 정보는 사용자 UI에서 제거한다.

- 서버 주소
- IP
- Session ID
- API 정보
- 디버그 정보

해당 정보는 관리자/디버그 패널(UI 설계 ②의 Connection 화면)로 이동한다.

색상과 버튼 규칙은 [6장 디자인 시스템](#6-디자인-시스템)을 따른다.

## 16. S01 — 창고 만들기

### 16.1 기본 화면

```text
┌─────────────────────────────────┐
│ ① 창고 만들기          ● 연결됨 │
├─────────────────────────────────┤

│          └────────┘             │
│                                 │

│                                 │
├─────────────────────────────────┤
│       [ 직접 입력하기 ]          │
└─────────────────────────────────┘
```

주요 버튼:

- `말하기`
- `직접 입력하기`

기존의 `누르고 말하기`보다 사용자의 행동을 직접 나타내는 `말하기` 또는 `말해서 만들기`와 같은 표현을 사용한다.

### 16.2 직접 입력 모드

```text
┌─────────────────────────────────┐
│ ① 창고 만들기                   │
├─────────────────────────────────┤
│                                 │
│ 창고 조건을 입력하세요.          │
│                                 │
│ ┌─────────────────────────────┐ │
│ │ 랙 8줄, 통로 폭 3m,         │ │

│ └─────────────────────────────┘ │
│                                 │
├─────────────────────────────────┤
│ [ 취소 ]          [ 생성하기 ]  │
└─────────────────────────────────┘
```

### 16.3 음성 입력 상태

말하기를 누르면 다음 상태로 전환한다.

```text
┌─────────────────────────────────┐
│ ① 창고 만들기                   │
├─────────────────────────────────┤
│                                 │
│              🔴                 │
│                                 │
│          듣고 있습니다           │
│                                 │
│             00:04               │
│                                 │
│       "말씀해주세요..."          │
│                                 │

└─────────────────────────────────┘
```

음성 입력 상태:

```text

 ↓

 ↓

 ↓

```

### 16.4 STT 결과 확인

녹음이 끝나면 바로 창고를 생성하지 않고 사용자가 인식 결과를 확인할 수 있도록 한다.

```text
┌─────────────────────────────────┐

└─────────────────────────────────┘
```

- STT 오류 확인
- 다시 녹음
- 생성 실행

### 16.5 Agent 처리 화면

기존의 큰 빈 `Agent` 영역을 없애고 Agent의 현재 작업 상태를 보여준다.

```text
┌─────────────────────────────────┐
│        창고를 만들고 있어요      │
├─────────────────────────────────┤
│                                 │
│  ✓ 요구사항 확인                │
│                                 │
│  ✓ 창고 구조 생성               │
```

- 창고 생성: 진행 상태

- 병목 분석: 설명 및 개선안

## 21. S06 ~ S08 — 분석과 개선

### 21.1 S06 — 병목 분석

분석 기능은 별도의 중요 기능으로 강조한다.

```text
┌─────────────────────────────────────┐
│ 🔍 병목 분석                         │
├─────────────────────────────────────┤
│                                     │
│ ⚠ 주요 병목 발견                    │
│                                     │
│ 출하 도크 앞                        │
│ 위치 (12, 3)                        │
│                                     │
│ 대기 횟수  37회                     │
│                                     │
├─────────────────────────────────────┤
│ 🤖 Agent 분석                       │
│                                     │
│ 출하 도크 앞의 한 통로에 로봇이     │
│ 집중되어 대기가 발생했습니다.       │
│                                     │
├─────────────────────────────────────┤
│ 개선안                               │
│                                     │
│ [ 보관 위치 분산 ]                   │
│ [ 경로 분산 ]                       │
│                                     │
│              [ 닫기 ]               │
└─────────────────────────────────────┘
```

### 21.2 병목 위치의 3D 표시

분석 패널에 위치 정보만 표시하지 않고 3D 공간에서도 해당 위치를 강조한다.

```text
             🤖
              ↓
       ┌─────────────┐
       │      🔴     │ ← 병목 마커
       │             │
       └─────────────┘
```

다시 말해,

```text
3D 병목 마커
      ↕
분석 패널
```

이 서로 연결되어야 한다.

### 21.3 S07 — 개선안 선택 및 승인

개선안을 선택한 뒤 바로 적용하지 않고 사용자 승인을 받는다.

```text
┌─────────────────────────────────┐
│       개선안을 적용할까요?       │
├─────────────────────────────────┤
│                                 │
│ 선택한 개선안                    │
│                                 │
│ "보관 위치를 분산합니다."        │
│                                 │
│ 예상 효과                        │
│ • 특정 구역 집중 완화            │
│ • 로봇 경로 분산                 │
│                                 │
├─────────────────────────────────┤
│ [ 취소 ]             [ ✓ 적용 ] │
└─────────────────────────────────┘
```

사용자가 `적용`을 누른 뒤에만 재시뮬레이션을 실행한다.

### 21.4 S08 — 개선 후 결과

개선 전과 개선 후를 직접 비교한다.

```text
┌─────────────────────────────────┐
│          개선 결과              │
├─────────────────────────────────┤
│                                 │
│        적용 전     적용 후       │
│                                 │
│ 대기     187       121          │
│ 처리     420       350          │
│                                 │
│        ↓ 개선 결과 ↓             │
│                                 │
│ [ 개선 전 ]      [ 개선 후 ]    │
│   히트맵           히트맵        │
│                                 │
├─────────────────────────────────┤
│       [ 다시 시뮬레이션 ]        │
└─────────────────────────────────┘
```

Agent의 정성적인 설명뿐 아니라 전/후 수치를 함께 보여주는 것이 이 화면에서 가장 중요하다.

## 25. Agent UI의 역할 재정의

Agent를 하나의 큰 고정 패널로 두지 않는다.

Agent는 사용자의 작업 단계에 따라 다른 역할을 한다.

| 단계 | Agent 역할 |
|---|---|
| 창고 생성 | 진행 상태 |
| 검증 실패 | 사용자 질문 |
| 시뮬레이션 | 진행 상태 |
| 병목 분석 | 원인 설명 |
| 개선안 | 개선 방향 제시 |
| 개선 적용 | 결과 비교 지원 |

정리하면,

```text
기존

[ Agent ]
  ↓
항상 큰 영역


개선

창고 생성 → [ 생성 진행 상태 ]

검증 실패 → [ Agent 질문 ]

병목 분석 → [ Agent 분석 ]

개선안 → [ Agent 개선 제안 ]
```

으로 변경한다.

## 26. 화면별 Primary Action

한 화면에서 가장 중요한 행동을 하나로 정한다.

| 화면 | Primary Action |
|---|---|
| 창고 만들기 | 말하기 |
| STT 결과 | 생성하기 |
| Agent 처리 | 없음 |
| 창고 확인 | 확인 |
| 검증 실패 | 질문에 응답 |
| 시뮬레이션 설정 | 시뮬레이션 실행 |
| 시뮬레이션 실행 중 | 없음 |
| 재생 | 재생/일시정지 |
| 병목 분석 | 분석 결과 확인 |
| 개선안 | 적용 |
| 개선 결과 | 다시 시뮬레이션 |

## 28. 최종 사용자 UI 설계 원칙

1. **3D 창고를 주 화면으로 한다.**
2. UI는 작은 World Space 패널로 구성한다.
3. 한 화면에 Primary Action을 하나만 둔다.
4. 서버/IP/Session ID 등의 개발자 정보를 사용자 UI에서 제거한다.
5. W1~W6과 같은 내부 식별 버튼을 제거한다.
6. Agent를 하나의 큰 고정 패널로 만들지 않는다.
7. Agent는 작업 단계에 따라 진행 상태, 질문, 분석, 개선안으로 역할을 바꾼다.
8. 창고 생성 → 확인 → 시뮬레이션 → 결과 분석의 4단계 흐름을 명확하게 표시한다.
9. 음성 입력과 Quest 2 컨트롤러 입력을 함께 사용한다.
10. 병목 분석에서는 3D 위치와 분석 패널을 연결한다.
11. 개선안은 사용자 승인 후 적용한다.
12. 개선 전/후 결과를 수치와 시각화로 비교한다.
13. 버튼의 Normal/Hover/Pressed/Disabled 상태를 통일한다.
14. 화면마다 사용자가 지금 해야 할 행동이 명확하게 보여야 한다.
15. 개발자/관리자 기능은 사용자 UI와 분리한다.

## 29. 사용자 UI 다음 설계 단계

이 사용자 UI 설계를 기반으로 다음 3가지를 구체화한다.

### A. Quest 2 실제 화면 목업

- 패널 실제 위치
- 패널 크기
- 버튼 크기
- 텍스트 크기
- 3D 공간과 UI의 관계
- 시선/컨트롤러 포인터 기준

### B. Unity 구현 구조

```text
Canvas
 ├─ Header
 ├─ Progress
 ├─ User Panels
 └─ Feedback
```

을 실제 Prefab 구조와 컴포넌트 수준으로 구체화한다.

### C. UI State Machine

```text
CREATE
 ↓
STT
 ↓
GENERATING
 ↓
CONFIRM
 ↓
VALIDATION_ERROR
 ↓
SIMULATION_CONFIG
 ↓
SIMULATING
 ↓
PLAYBACK
 ↓
ANALYSIS
 ↓
PROPOSAL
 ↓
APPROVAL
 ↓
COMPARISON
```

형태로 실제 화면 전환 조건과 버튼 동작을 정의한다.
