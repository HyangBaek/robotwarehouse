## 1. 개요

### 1.1 목적

이 문서는 로봇웨어하우스 시스템이 무엇을 해야 하는지 정의한다. 팀원 3명이 같은 기준으로 개발·테스트하고, 완료보고서와 발표자료에서 "무엇을 만들었는가"를 설명하는 근거로 쓴다.

### 1.2 시스템 범위

사용자가 Meta Quest 2 VR 안에서 창고 구조를 말이나 텍스트로 설명하면, AI Agent가 이를 격자 지도로 구성·검증하고, 다중 로봇의 작업 할당과 경로를 계산해 VR 공간에서 동선과 혼잡도를 보여 준다. 이어서 이동 로그를 분석해 병목 원인과 개선안을 제시한다.

**범위 밖**
- 실제 물류 설비 제어, 실시간 센서·위치 연동
- 사람이 모는 지게차가 섞인 혼재 운영
- 가감속·회전 반경을 반영한 실제 소요 시간 추정
- 도면(CAD) 파일 입력, 다층 랙 3D 동선
- 상용 수준의 보안 체계, 다중 사용자 동시 접속

### 1.3 용어

| 용어 | 정의 |
|---|---|
| 격자 지도 | 창고를 1m × 1m 칸으로 나눈 JSON 데이터. 칸 한 개는 로봇 한 대 크기 |
| 칸 유형 | 통로(aisle), 랙(rack), 벽·기둥(wall), 입하 도크(dock_in), 출하 도크(dock_out), 충전·대기(charge) |
| 시나리오 | 입출하 주문 수량·규격과 가동 로봇 수의 조합 |
| 스텝 | 시뮬레이션 시간 단위. 로봇은 한 스텝에 한 칸 이동하거나 대기 |
| 기준 전략 | 무작위 보관 위치 + 선착순 작업 할당 + 로봇별 개별 최단 경로 |
| 최적화 전략 | 보관 위치 선정 + 가장 가까운 유휴 로봇 우선 할당 + 충돌을 고려한 다중 로봇 경로 계획 |
| E2E 흐름 | 음성·텍스트 입력 → 격자 지도 생성 → 경로 계산 → VR 이동 재생 |

## 2. 전체 설명

### 2.1 사용자

| 사용자 | 특징 | 요구 |
|---|---|---|
| 창고 운영·기획 담당자 (주 사용자) | 중소 물류·제조 기업 소속. 시뮬레이터·경로 계획 지식 없음 | 말로 창고를 만들고, 로봇 수·물량을 바꿔 가며 처리 성능과 병목을 도입 전에 확인 |
| 심사위원 (시연 관람자) | 짧은 시간 안에 Agent 동작을 판단 | 입력 → 판단 → 도구 실행 → 결과가 눈에 보여야 함 |

### 2.2 운영 환경

| 구분 | 환경 |
|---|---|
| VR 디바이스 | Meta Quest 2 (대회 대여 장비), 개발자 모드 |
| VR 클라이언트 | Unity + Meta XR SDK, C# |
| 서버 | 팀 노트북, Python, FastAPI, LangGraph, NumPy, SQLite |
| 외부 서비스 | LLM API(GPT-4 계열), Whisper STT, TTS API |
| 네트워크 | Quest 2와 서버 노트북이 같은 Wi-Fi에 연결 |
| 선택 자원 | 대회 제공 GPU 서버 (대규모 비교 실험 시) |

### 2.3 제약 조건

- **C-01** 개발 기간은 2026-09-29 ~ 10-06(8일)이며, 기간 외에 사전 개발한 코드는 쓰지 않는다.
- **C-02** 제출물은 Quest 2에 설치 가능한 VR 소프트웨어여야 한다.
- **C-03** 완성도는 최소 Level 2(Prototype), 목표는 Level 3(MVP: 최소 1개 E2E 흐름의 안정 동작)이다.
- **C-04** AI 도구·공개 코드·모델·데이터·외부 API의 출처는 별지2에 모두 적는다.
- **C-05** 경로 계획 알고리즘은 공개 논문의 방법을 참고하되 팀이 직접 구현한다.

### 2.4 가정

- **A-01** 사람 없이 로봇만 운영하는 완전 무인 창고를 가정한다.
- **A-02** 로봇 속도와 작업 시간은 설정한 가정값이다. 처리 시간은 스텝 단위의 시뮬레이션 값이며 상대 비교 용도로 쓴다.
- **A-03** 파레트·상자 치수와 물동량은 공개된 표준 수치를 기본값으로 쓴다.

## 3. 기능 요구사항

> 형식: ID · 요구사항 · 우선순위 · 담당 · 수용 기준(테스트로 확인할 조건)

### 3.1 자연어 기반 창고 구성 (신청서 기능 ①)

| ID | 요구사항 | 등급 | 담당 | 수용 기준 |
|---|---|:-:|---|---|
| FR-01 | 사용자는 VR에서 창고 구조를 텍스트로 입력할 수 있다 | P0 | 백향·방유진 | VR 입력 패널에서 보낸 텍스트가 서버에 도착한다 |
| FR-02 | 사용자는 VR에서 창고 구조를 음성으로 입력할 수 있다 | P0 | 방유진·백향 | Quest 2에서 녹음한 음성이 STT로 변환되어 텍스트로 표시된다 |
| FR-03 | Agent는 입력 문장에서 랙 줄 수, 통로 폭, 입하·출하 도크 수, 충전 구역 등 요구사항을 추출한다 | P0 | 방유진 | 테스트 문장에서 추출한 항목이 기대값과 일치한다 |

### 3.2 창고 지도 검증 및 수정 (신청서 기능 ②)

| ID | 요구사항 | 등급 | 담당 | 수용 기준 |
|---|---|:-:|---|---|
| FR-06 | 시스템은 격자 지도의 형식(필수 필드, 칸 유형 값, 크기 일치)을 검사한다 | P0 | 방유진 | 형식이 잘못된 지도를 넣으면 오류 항목을 반환한다 |
| FR-07 | 시스템은 모든 랙 칸과 도크가 통로로 도달 가능한지 검사한다 | P0 | 방유진·하재윤 | 막힌 랙이 있는 지도를 넣으면 해당 좌표를 반환한다 |
| FR-08 | 검증에 실패하면 Agent가 수정이 필요한 항목을 사용자에게 질문하고, 답변을 반영해 지도를 다시 만든다 | P0 | 방유진 | 실패 → 질문 → 답변 → 재생성 → 통과까지 한 번 이어진다 |

| FR-10 | 사용자는 VR에서 랙을 잡아 옮겨 지도를 직접 고칠 수 있고, 고친 지도는 다시 검증된다 | P2 | 백향 | 랙을 옮긴 뒤 서버 지도와 VR 배치가 일치하고, 검증 결과가 갱신된다 |

## 4. 비기능 요구사항

> 수치는 팀 목표값입니다. 10/2 통합 빌드 후 실측해 조정합니다.

| ID | 분류 | 요구사항 | 목표·측정 방법 |
|---|---|---|---|
| NFR-01 | 성능 | VR 재생 중 프레임을 유지한다 | 로봇 `[N]`대 재생 시 Quest 2 평균 FPS `[목표값]` 이상. 기본 도형과 인스턴싱 렌더링 사용 |

| NFR-03 | 성능 | 롤링 재계획 시간을 측정한다 | 물량·로봇 수 조합별 재계획 시간을 기록 (신청서 정량 목표) |

| NFR-06 | 신뢰성 | LLM 응답이 스키마를 벗어나도 시스템이 멈추지 않는다 | 잘못된 JSON이 오면 오류 메시지를 띄우고 재시도나 수정 질문으로 넘어간다 |
| NFR-07 | 사용성 | 경로 계획을 모르는 사용자가 말과 손만으로 창고를 구성할 수 있다 | 팀 외 사용자 1~2명이 안내 없이 E2E 흐름 완료 |
| NFR-08 | 설명 가능성 | 개선안은 히트맵 위치와 로그 수치를 근거로 제시된다 | FR-27 수용 기준과 동일 |
| NFR-09 | 이식성 | 창고 크기·구조가 달라도 같은 알고리즘이 동작한다 | 구조가 다른 시나리오 3개(S1~S3)에서 E2E 성공 |
| NFR-10 | 보안 | API 키를 코드와 저장소에 넣지 않는다 | `.env`로 분리, 커밋 이력 점검 |
| NFR-11 | 유지보수 | VR·엔진·Agent가 하나의 격자 지도 스키마를 쓴다 | 스키마 변경 시 `docs/schema.md`와 버전 필드를 함께 갱신 |
| NFR-12 | 재현성 | 심사위원이 README만 보고 실행할 수 있다 | 팀원 1명이 새 환경에서 README 순서대로 실행 성공 |

## 5. 데이터 요구사항

### 5.1 격자 지도 스키마 (DR-01)

```json
{
  "schema_version": "1.0",
  "cell_size_m": 1.0,
  "width": 30,
  "height": 20,
  "cells": [
    {"x": 0, "y": 0, "type": "wall"},
    {"x": 3, "y": 2, "type": "rack", "rack_id": "R01"}
  ],
  "racks": [
    {"rack_id": "R01", "levels": 3, "slot_spec": "pallet_1100x1100", "capacity": 6}
  ],
  "docks": [
    {"dock_id": "IN1", "type": "dock_in", "x": 0, "y": 10}
  ],
  "rules": {
    "one_way": [{"from": [5, 1], "to": [5, 18], "dir": "N"}],
    "passing_allowed": [[10, 1], [10, 18]]
  }
}
```

| 필드 | 필수 | 설명 |
|---|:-:|---|
| `schema_version` | O | 스키마 버전. VR·엔진·Agent가 같은 버전인지 확인 |
| `width`, `height` | O | 격자 크기(칸 수) |
| `cells[].type` | O | aisle / rack / wall / dock_in / dock_out / charge. 지정하지 않은 칸은 aisle |
| `racks[]` | O | 랙 ID, 단 수, 칸별 수용 규격, 용량 |
| `docks[]` | O | 입하·출하 도크 위치 |
| `rules` | - | 일방통행 구간, 엇갈림 가능 구간 |

> 필드 이름과 값은 9/29에 확정한 스키마로 바꿔 적습니다.

### 5.2 시나리오 (DR-02)

| 필드 | 설명 |
|---|---|
| `scenario_id` | 시나리오 식별자 (S1, S2 …) |
| `map_version` | 사용한 격자 지도 버전 |
| `robots` | 가동 로봇 수, 시작 위치 |
| `orders[]` | 주문 ID, 유형(입하/출하), 제품 규격, 수량, 도착 스텝 |
| `strategy` | baseline / optimized |

### 5.3 시뮬레이션 로그 (DR-03)

| 데이터 | 형식 | 용도 |
|---|---|---|
| 스텝별 로봇 위치 | `{t, robots: [{id, x, y, state, task_id}]}` | VR 재생 (FR-21) |
| 주문 처리 기록 | `{order_id, robot_id, assigned_t, done_t}` | 처리 시간 집계 (FR-25) |
| 칸별 통과·대기 | `{x, y, pass, wait}` | 히트맵·병목 추출 (FR-24, FR-26) |
| 충돌 검사 결과 | `{t, robot_a, robot_b, x, y, type}` | 신뢰성 검증 (NFR-04) |

모든 로그는 `scenario_id`, `strategy`, `map_version`과 함께 SQLite에 저장한다.

## 6. 인터페이스 요구사항

| ID | 구간 | 방식 | 요구사항 |
|---|---|---|---|
| IR-01 | VR → 서버 | REST (HTTP·JSON) | 창고 설명(텍스트·음성 파일), 시나리오, 수정 답변, 지도 확인, 개선안 승인 전송 |
| IR-02 | 서버 → VR | WebSocket | 격자 지도 JSON, 스텝별 로봇 위치 프레임, 칸별 집계, 분석 결과·질문 텍스트 전송 |
| IR-03 | 서버 ↔ LLM | HTTPS API | 도구 호출 형식(function calling 등)으로 응답을 받아 스키마 검증 후 사용 |
| IR-04 | 서버 ↔ STT·TTS | HTTPS API | 음성 파일 → 텍스트, 텍스트 → 음성 파일 |
| IR-05 | 도구 ↔ 경로 계산 엔진 | Python 함수 호출 | 입력: 격자 지도, 시나리오 / 출력: DR-03 로그 |
| IR-06 | VR 사용자 인터페이스 | Quest 2 컨트롤러 | 입력 패널, 녹음 버튼, 재생 컨트롤(재생·일시정지·배속), 경로 선·히트맵 토글, 결과 패널(질문·개선안·승인) |

> 엔드포인트 이름과 메시지 필드는 `docs/api.md`(9/29 확정 명세)를 따릅니다. 이 문서와 다르면 `docs/api.md`가 우선입니다.
